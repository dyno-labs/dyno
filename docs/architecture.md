# Architecture

dyno is one Rust binary built from a Cargo workspace. The skeleton has the full command line and the full result shape. Every measure is a stub that reports `missing` with the reason "not built yet", or `unsupported` when the input cannot give it. Each later step fills in stubs and does not change the shape.

## How a check runs

1. `dyno-static` scans the build, if there is one. The families run in the order of the data flow: inventory, bundle, textures, audio, bytes, duplicates. Then the static rules run on their summaries, the host profile and the budget file. Without a build, every static measure is `unsupported` and every static rule is `incomplete`.
2. `dyno-score` checks each budget in the budget file against its static measure. A value with a gap in its scope is a floor, so it gives a verdict only when no bigger value could give a worse one. Otherwise the budget is incomplete. A rule's threshold gives no verdict: its rule checks it.
3. `dyno-score` adds the model measures, which are `unsupported` without a launch URL. With a launch URL, or a build that `--browser` or `--driver serve` serves, `dyno-run` runs the browser through a driver. With `--device`, `dyno-ios` adds the device measures.
4. `dyno-score` works out from the inputs which measures each part must have. It sets the run coverage from the run measures, then the overall status from the static measures, the budget verdicts, the static findings and the run coverage.
5. `CheckResult::new` in `dyno-schema` makes a measure with a bad number invalid, sorts every list, rejects a repeated measure id, budget id or file path, and computes the hash.

## Rules for each step

- **Keep the shape.** Add fields and measures. Do not rename or remove them. A breaking change bumps `SCHEMA_VERSION`.
- **One place for ids.** Every measure, rule and budget id is defined in `dyno-schema/src/ids.rs`. A measure's entry in `ids.rs` also gives its source, phase, unit, what it covers, its quantity (what it counts) and its statistic (which reading it is). No two measures of one source share a quantity and a statistic, and a test checks it. Each static measure belongs to exactly one family's `MEASURES` list, and a test checks that too.
- **Static values are `estimated`.** Only browser and device readings are `measured`.
- **Nothing in the deterministic part may depend on the machine.** Use integer bytes, relative `/` paths and sorted lists. Timestamps, paths as given, URLs and labels go in the `run` part. The one exception is the run coverage, and the status that follows it. It stays in the hashed part so that the hash always gives the exit code. A build-only check has no run coverage to vary, so its hash reproduces on any machine. A check with a launch URL or `--device` gets a hash that identifies its result, but it is not expected to reproduce.
- **Static findings count toward the status.** A finding that warns or fails gives that status. An incomplete one counts only when a value from the build is missing, not when the rule is not built yet or reads an `unsupported` measure. Lab findings are in the run part, so they do not count.
- **Outside text is scrubbed where it comes in.** A driver error is a fixed code plus a detail that `DriverError::new` runs through `dyno_schema::scrub::scrub`. So no driver in another crate can put the user info, query string or fragment of a URL with a `://` into a reason. Use the same scrub for any other driver or subprocess text.
- **The runner protocol messages are in `dyno-schema`, not `dyno-run`.** The fallback driver is a TypeScript script, so the messages need generated TypeScript types like the probe events.

## The browser run

`dyno_cdp::run_cdp` serves a harness page on a local site that is never the game's, launches Chromium headless with site isolation, `--force-device-scale-factor` from the host profile and WebGPU only when the host profile has it (on Linux, where WebGPU runs on SwiftShader's Vulkan; on a Mac, Chrome's GPU gives WebGPU whatever the profile says), gives the page the host profile's viewport by emulation, and attaches to it with every frame paused before its first script. The first frame the page attaches is the game frame; every target attached under it, such as a nested frame or a worker, joins its family, and the family's requests are the game's (`data:` and `blob:` URLs cross no network, so they do not count). Before it runs, the driver enables its network, adds the `__dynoProbe` binding and the probe, and auto-attaches its own children. The probe sends each event to the binding. It numbers each canvas and each WebGL texture, so a resize, a re-upload of a texture level or a deleted texture can be followed. The harness page reports each message the game sends it through `__dynoHost`; the driver puts it on the frame's clock with the frame's `performance.timeOrigin`. Requests are joined by request id across sessions, and a request counts when it ends on the game frame's session. The frame is idle when no request is in flight and none started for `idle_after_ms`. Then the driver reads the heap, runs the self-checks in an isolated world (so the probe's wrappers do not see them) and records when the frame's clock started on its own clock, sends the host profile's active message, watches for 2 s and ends with `done`. `timeout_ms` bounds the whole run, calls included; a run that reaches it ends with `error`. Chromium gets 5 s to exit after `Browser.close`, and its profile is deleted after it.

`dyno check --driver exec:<program>` uses `dyno_run::exec::ExecDriver` instead. It lets an outside program run the browser, such as a Playwright script or a driver that is not in this repo, with no change to dyno. dyno starts the program directly, with no shell and no arguments. It writes the `RunRequest` as one JSON line on the program's stdin and closes stdin. The program writes the same `DriverMessage` lines on stdout that the CDP driver gives: `hello` with `RUNNER_PROTOCOL_VERSION` first, and `done` or `error` last. dyno stops reading at that last message. So `lab` gives the same measures from both drivers. These are protocol errors: a line that is not a message, a first message that is not a `hello` with the same protocol version, and a stdout that closes before `done` or `error`. The last error quotes the end of the program's stderr. `timeout_ms` bounds the whole run. At the deadline, dyno kills the program and the run fails. A program that sent its last message gets 5 s to exit, then dyno kills it. dyno reads stderr on its own thread, so a program that writes much to stderr never stops. Every error detail goes through `DriverError::new`, so the scrub removes secrets from the quoted stderr too.

`dyno check <build> --browser` runs the same CDP run on the build folder itself. Before the run, `check_one` starts `dyno_serve::BuildServer`: the served run's game server on a thread of its own, on a free port of 127.0.0.1, with no harness page and no probe tag, as the CDP driver adds the probe itself. It serves the same files, with the same content types, byte ranges, `no-store` and path checks. The run request's launch URL is the server's root, so the CDP harness page is on `localhost` and the game frame stays cross-site. The build link is `served`, and the server stops when the check ends.

The CLI tests set `DYNO_CHROMIUM` to a path that does not exist, so a check with a launch URL fails the same way on every machine. The Chromium test in `crates/dyno-cdp/tests/chromium.rs` and the probe freshness test are ignored by default: they need Chromium and Node. Run them with `cargo test -p dyno-cdp -- --ignored`.

## The served run

`dyno check <build> --driver serve` uses `dyno_serve::ServeDriver`. dyno binds two ports on one host: the harness page on the first, and the build folder on the next, so the game frame is cross-origin to the page around it. No browser starts: a person, or a tool such as `xcrun simctl openurl`, opens the harness page on any device that reaches this machine. The page posts `hello`, and dyno answers once it has started its clock (`navigated`). Only then does the page set the frame's URL, so every game request comes after the navigation. The run request's launch URL is the game server's URL with the `--serve-query` query string.

The game server adds `<script src="/__dyno/probe.js" data-dyno-relay>` at the start of each HTML page's `<head>`, and serves the lab build of the probe there. A script from the game's own origin runs under a policy that allows only `'self'`. With `data-dyno-relay` and no driver binding, the probe in the game frame posts each event to the harness page; a frame inside the game frame posts nothing. Its first post gives the document's `performance.timeOrigin` and pixel ratio, which becomes a `frame_document` mark. The harness page sends what it receives to `/__dyno/events` every 250 ms, and polls `/__dyno/next` for commands: the self-check, the active message, a flush and the end of the run. An answer goes last in the batch that holds the events before it, so dyno reads them first.

Every request to the game server, but the probe's own under `/__dyno/`, is a game request. Its URL has no query string. The frame is idle when a document has loaded the probe, no game request is in flight and none started for `idle_after_ms`. Then dyno asks for the self-check (the frame's pixel ratio from the probe, and the page's WebGL renderer), sends the profile's active message, watches for 2 s, and asks the page for everything it still holds, because a browser can slow the 250 ms timer in a page it does not show. A page that does not send them within 5 s ends the run with an error, and a batch that fails to send goes back in the page's queue. A second page that posts `hello` in the same run gets `409`. Files are served with their content type, `Cache-Control: no-store`, and single byte ranges, which Safari needs for media. A path that leaves the build, by `..` or by a link, is `404`.

The driver's clock is this machine's, from its answer to `hello`. The frame's clock is placed on it by the browser's own wall clock: `frame_clock_at_ms` is the frame's `timeOrigin` minus the time the page set the frame's URL. Messages to the host are placed on the frame's clock in the same way.

## The device run

`dyno check <build> --driver serve --device` runs on any machine that reaches the phone, on Linux or macOS. Before it prints the URL, `dyno_ios::Recorder` starts a thread with a tokio runtime, and `dyno_ios::phone` reaches the phone with the `idevice` crate: through usbmuxd (`--device-id`, or the only phone it lists), which holds the pair record, or straight at `--device-ip` with the pair record in `--pairing-file`. It opens the phone's CoreDevice tunnel (iOS 17 and later), finds the services with RSD, and opens Instruments' sysmontap service through the tunnel and the syslog relay through lockdown. The tap takes a config only with every process and system attribute the phone lists, so dyno asks for all of them and reads `pid`, `name` and `physFootprint` by their place. idevice's own sysmontap client keeps only the first row of each message and loses the processes, so dyno reads the tap's channel itself and merges every row. Through the tunnel, the syslog relay serves no one for about a minute after a client goes, so the second run of `--runs` got no lines; through lockdown it serves the next client at once. Once both sources send, the recorder asks CoreDevice's app service to launch Safari with the harness page as its payload URL, as `devicectl device process launch --terminate-existing --payload-url` does. When the phone says it is locked, the check stops. When the launch fails on a Mac, or with `DYNO_XCRUN`, dyno tries `xcrun devicectl`. Otherwise it says to open the page by hand. The page waits in the listen backlog until the run starts. When the run ends, dyno tells the recorder to stop and takes the recording.

The recording (`dyno_ios::recording`) keeps each sample of a Safari WebContent process and each kernel `memorystatus` line, stamped with this machine's clock as they arrive. Samples come about once a second, and over Wi-Fi the gap between two was at most 2.7 s. A source that fails, or that sends nothing for 10 s before the stop, covers the recording only up to the last thing it sent. The served run records when it answered `hello`, when the frame went idle and when it ended, on the same clock (`ServeDriver::last_run`), so the run's steps fall on the samples with no clock to join. `dyno_ios::device_measures` takes the WebContent process with the largest footprint during the run as the game's, reads its footprint at the first sample after idle and its peak in the run, and counts a kill when the log has a jetsam kill of its pid during the run: `memorystatus: killing process <pid> [...]`, `killing_<kind> pid <pid> [...]`, or a fatal `exceeded mem limit` line. `killing_idle_process` lines are Safari's idle pages exiting, not kills. Sysmon can leave a live process out of a sample, so a process that leaves the samples is not a kill. The kernel's other lines about the process, such as a soft memory limit it went over, go into the evidence of `device.kills`. Samples that ended more than 3 s before the run did give no peak, and a log that did gives no `device.kills`, unless it saw the kill. `dyno_ios::phone_environment` names the model from its identifier (`ProductType` in the RSD handshake, through the device catalogue), the iOS version and build from the handshake, and the memory from the tap's `physMemSize`, in 16 KiB pages.

With `--runs N`, `check_one` writes the empty build and runs it and the game in turn, N times each. Each run binds its own `ServeDriver` on the same ports, starts its own recording, opens the page in a fresh Safari and reads its own device measures. `dyno_ios::runs::device_runs_measures` then takes the median of the game runs' readings, counts their kills, and subtracts the median peak of the empty build runs for `device.footprint_over_baseline`. A run with no reading leaves the measures that need it missing, with the run in the reason. The lab measures come from the first game run that completed. A run that never started, or a recording that did not end well, gives the device measures as missing, with the reason.

`dyno_ios::trace` reads an Activity Monitor trace that `xcrun xctrace export` gave: the table of contents and the `activity-monitor-process-live` table. `--device` does not use it. It stays for traces that another host records, such as a device cloud's phone through Appium's `mobile: startPerfRecord`, and `trace::device_measures` gives the same measures from one, with a kill when the game's process left the trace more than 3 s before the run ended.

## What ran

Each check makes a UUID v4 run id when it starts, and sets the build link from its target, its driver and `--browser`. `Driver::environment` gives what ran, from the run's `hello`: by default the browser it names, which is all an exec program says. The CDP driver adds headless and this machine's OS. The serve driver reads the user agent that the harness page sent (`dyno_serve::user_agent_environment`) instead. With `--device`, the phone's OS and device replace the user agent's. A run that fails before its `hello` has no environment. One that fails after it, as when iOS kills the page, keeps it.

`dyno_schema::link::find_link` reads the nearest `dyno.toml` above the build and finds its entry for the build, and `check_target` puts its game id and name in `run.release` when the command line gave none. With `--games`, each game is looked up before any check starts, so a bad file never leaves half a catalogue. `--baseline` writes the empty build to a temporary folder and checks it like any build, but records no target path and looks up no game.

## The MCP server

`dyno mcp` is a local MCP server on stdin and stdout. It uses `rmcp`, the official MCP Rust SDK, with only its server, its tool macros and its stdio transport. Its tools call the same functions as the commands: `check::check_target`, `compare::compare_files` and `compare::read_result`. These functions return the result and write nothing. The commands write the JSON and the summary after the call, so in MCP mode only MCP messages go to stdout. The server runs on a tokio runtime with one thread. The CDP driver starts its own tokio runtime, and a runtime cannot start inside another. So each tool call runs on its own thread, and the server waits for its answer.

## Generated files

`packages/schema/json/` and `packages/schema/ts/` are generated from `dyno-schema`, `fixtures/golden-hashes.json` from the fixtures, and the help and stub result snapshots are in `crates/dyno-cli/tests/snapshots/`. Tests fail when any of them is stale. After a change you make on purpose, run `DYNO_UPDATE_GENERATED=1 INSTA_UPDATE=always cargo test --workspace` to replace the saved copies with the new output, then read the diff.
